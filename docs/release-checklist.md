# 公開前チェックリスト

コード内の対策と、実際の本番サービス側で設定する作業を分けて記録します。ビルドや環境変数の形式チェックだけでは、サービスの公開準備が完了したことにはなりません。

## リリース時の確認

- [ ] 本番用の環境変数を設定し、`npm run check:production` を実行する。チェック対象はDB接続URLの形式、公開HTTPSオリジン、Clerk/Stripeの本番キー形式、両Webhook署名シークレット、32文字以上のCronシークレット、問い合わせメールアドレス。資格情報の有効性は各サービスで別途確認する。
- [ ] ステージングで `npm run prisma:deploy`、`npm run lint`、`npm run typecheck`、`npm test`、`npm run build` を実行する。マイグレーションの前にDBの復元可能なバックアップを確保する。
- [ ] 隔離したDBで `DATABASE_URL` と `TEST_DATABASE_URL` を同じ接続先にして統合テストを実行する。GitHub Actionsでは一時的なPostgreSQLを使い、統合テストを含めて実行する。CIは本番DBへ接続しない。
- [ ] ステージングで実際のStripeテスト決済を行い、予約確定、二重送信、キャンセル、返金、月額契約、継続請求、支払い失敗、解約、コンテンツ閲覧権限を確認する。自動テストではStripeをモックしており、実際のカード決済までは確認しない。
- [ ] Stripeにプラットフォーム用とConnect用のWebhookを別々に登録する。必要なイベントは [marketplace-workflows.md](marketplace-workflows.md) を参照する。Billing Portalで解約・支払方法変更を確認する。
- [ ] Clerkの本番ドメイン、サインイン・サインアップ・リダイレクト設定を確認する。
- [ ] `SUPPORT_EMAIL` に実際に受信できるアドレスを設定する。未ログイン・利用停止中の利用者が `/ja/support` と `/en/support` を開き、問い合わせできることを確認する。
- [ ] 15分ごとに `GET /api/cron/booking-reminders` を `Authorization: Bearer <CRON_SECRET>` 付きで実行するスケジューラーを設定する。`npm run maintenance` は同じエンドポイントを呼び出す手動・外部スケジューラー向けコマンド。
- [ ] スマートフォンで検索→予約→支払い→予約詳細の流れを確認する。英語・日本語の両方を確認する。

## 監視と復旧

- [ ] アプリの例外ログとStripe Webhookの失敗を監視し、担当者を決める。WebhookのDB記録は `StripeWebhookEvent` の `FAILED` と長時間残る `PROCESSING` を確認する。Stripeの再送は冪等処理される。
- [ ] CronのHTTP 503・タイムアウト・実行欠落を監視する。HTTP 200のJSONには `failed: 0` が入る。503になっても一部処理は完了しているため、ログと予約状態を確認したうえで再実行する。
- [ ] 返金失敗は `Booking.refundStatus = FAILED` を確認する。Cronが再試行するが、Stripe側の拒否や残高不足などは運用で解決する。Stripe上で手動返金する前に既存返金のIDと状態を確認する。
- [ ] DBバックアップの保持期間と復元手順を定め、ステージングで復元を試す。DB変更後にアプリだけを戻してよいか確認し、未検証の逆マイグレーションは実行しない。
- [ ] 障害時の案内、購入停止、返金・紛争処理の担当者と連絡先を記録する。

## 運営者による決定・追加実装が必要な項目

- [ ] 利用規約、プライバシーポリシー、運営者・販売者情報を公開する。予約キャンセル、サブスク解約、回数券の期限・返金条件、手数料の説明を実装と一致させる。実在する運営者情報や未決定の条件を仮の内容で掲載しない。
- [ ] 退会時の継続課金停止、個人情報の削除・匿名化、取引履歴の保持方針を決めて実装する。Clerkでユーザーを削除するだけではStripeの継続課金は停止しない。
- [ ] 利用停止時は既存予約・継続課金を運営者が確認する。`User.isActive = false` は利用と新規購入を制限するが、契約を自動解約しない。支払いWebhookと返金の処理は継続する。
- [ ] 公開APIへのアクセス制限・負荷対策をホスティング環境で設定し、検索の件数が増えたらページ分割・キャッシュ・DBクエリ数を検証する。アプリ内の分散レート制限はまだ実装されていない。
- [ ] LINEとアプリ独自のメール通知は未提供。公開案内に含めない。復旧する場合は [line-integration.md](line-integration.md) に従い、接続・通知・失敗時の再試行を検証する。

## 環境を混同しないための注意

ローカルのPrisma設定は `.env.local` を `.env` より優先します。注入した環境変数は維持されます。マイグレーションには `DATABASE_URL_UNPOOLED` が設定されていればそちらを使用します。テスト前・適用前に接続先のホストとDB名を確認してください。接続文字列やシークレットをログ・チケットへ貼り付けないでください。
